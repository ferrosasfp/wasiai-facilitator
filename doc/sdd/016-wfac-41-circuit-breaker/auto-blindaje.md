### [2026-04-23 08:00] Wave 1 — Route local-union forward-reference

- **Error**: extender `X402ErrorCode` con `'CHAIN_UNAVAILABLE'` rompió typecheck en `src/routes/verify.ts:175` y `src/routes/settle.ts:217` porque las uniones locales `VerifyRouteErrorCode` / `SettleRouteErrorCode` no incluían el nuevo literal, y la expresión `reply.code(result.error.http).send({ error: result.error })` hacía upcasting implícito del `X402ErrorCode` al union local (más angosto). Dos errores TS2322.
- **Causa raíz**: el Story File §0.6 dice "sin forward references" pero el Scope IN de W1 no incluye `src/routes/verify.ts`/`settle.ts`. Sin embargo el completion criterion de W1 exige `npm run typecheck` green. La única forma de mantener typecheck green tras extender `X402ErrorCode` es extender también las 2 uniones locales — no es forward-reference real (el cambio es sólo extender el union, no agregar lógica de handler de CHAIN_UNAVAILABLE, que sí vive en W4).
- **Fix**: extender `VerifyRouteErrorCode` y `SettleRouteErrorCode` con `| 'CHAIN_UNAVAILABLE' // WFAC-41` en W1. El handler completo (Retry-After header + body rebuild) sigue en W4. Esto es un patch mínimo de compatibility typecheck; el comportamiento en runtime no cambia hasta que un adapter pueda retornar `CHAIN_UNAVAILABLE` (W3).
- **Aplicar en**: cualquier HU futura que extienda `X402ErrorCode` — las uniones locales de `src/routes/*.ts` deben actualizarse en la misma wave que toca `src/core/types.ts`. Considerar si `VerifyRouteErrorCode` debería derivarse de `X402ErrorCode | 'INVALID_PAYLOAD'` en lugar de duplicar la lista — backlog técnico para reducir este maintenance burden.

### [2026-04-23 09:30] Wave 2 — ESLint unused eslint-disable directive

- **Error**: `readCbNumber` y `readCbBool` tenían `// eslint-disable-next-line security/detect-object-injection` tanto a nivel de la declaración de función (arriba de `export function`) como en la línea de `process.env[name]`. ESLint reportó los function-level disables como "Unused eslint-disable directive" (2 warnings → fail por `--max-warnings 0`).
- **Causa raíz**: el disable function-level se aplicaba al `name: string` parameter — pero el parameter por sí mismo no dispara `security/detect-object-injection` en eslint-plugin-security (v1.x). Solo dispara cuando `name` se usa como índice dinámico de objeto. El disable correcto es **solo** en la línea del acceso `process.env[name]`.
- **Fix**: remover los `eslint-disable-next-line` a nivel función; conservar únicamente los `eslint-disable-next-line` justo antes de `const raw = process.env[name];`. Agregar justificación en el comment del disable (por qué `name` no es user-controlled).
- **Aplicar en**: cualquier helper que lea `process.env[<caller-controlled-literal>]` — mantener el `eslint-disable` **solo** en la línea del acceso dinámico, nunca arriba de la declaración de función. Grep de verificación: `npm run lint` con `--max-warnings 0` debe pasar; si aparecen "Unused eslint-disable directive", remover esos comments específicos.

### [2026-04-23 09:45] Wave 2 — @typescript-eslint/consistent-type-imports prohibe inline import()

- **Error**: `cb.setLogger({ warn: warnSpy } as unknown as import('pino').Logger)` en tests disparó `@typescript-eslint/consistent-type-imports` — "`import()` type annotations are forbidden".
- **Causa raíz**: la regla de ESLint configurada prefiere `import type { X } from 'pino'` a top-level en lugar de `import('pino').X` inline. Es un patrón de consistencia (y mejor tree-shaking con `verbatimModuleSyntax`).
- **Fix**: agregar `import type { Logger } from 'pino';` al top del test file; reemplazar `as unknown as import('pino').Logger` por `as unknown as Logger`.
- **Aplicar en**: CUALQUIER archivo (source o test) que use un tipo de un paquete externo en una anotación. Prefiere `import type` top-level. También aplica a `src/app.ts` donde el cast de `FastifyBaseLogger → Logger` requiere `import type { Logger } from 'pino'` top-level.

### [2026-04-23 10:45] Wave 4 — FastifyBaseLogger no es estructuralmente compatible con pino.Logger

- **Error**: `initChainBreakers(app.log)` dio `TS2345: Argument of type 'FastifyBaseLogger' is not assignable to parameter of type 'Logger'. Property 'msgPrefix' is missing in type 'FastifyBaseLogger' but required in type 'BaseLogger'.`
- **Causa raíz**: Fastify expone `app.log: FastifyBaseLogger` que es un **subconjunto** estructural de `pino.Logger` (omite `msgPrefix`, propiedades internas de pino). En runtime la instancia ES un `pino.Logger` real (Fastify v5 lo crea así cuando `loggerInstance` es pino), pero TS ve el tipo estático más angosto.
- **Fix**: cast explícito `app.log as unknown as Logger` con `import type { Logger } from 'pino'` top-level. Comentario justificando por qué el cast es seguro (structural compatibility at runtime; missing field es unused pino internal).
- **Aplicar en**: cualquier helper que acepte `pino.Logger` y se llame desde código Fastify (`app.log` / `request.log` / `reply.log`). Documentar el cast con un comment que referencie este auto-blindaje. Alternativa futura: cambiar la firma de `initChainBreakers` a `FastifyBaseLogger` — pero eso acoplaría `src/chains/init-breakers.ts` a Fastify, violando OWNERS (chains/* no importa infra/* ni routes/*). Mantener `pino.Logger` + cast es la opción correcta.

### [2026-04-23 12:30] Fix-pack post-AR/CR — AC-13 double-counting via inner policy.execute

- **Error (AR-BLQ-ALTO-1 / BLOQUEANTE)**: tras los tests sintéticos (T-CB-9) AC-13 se veía verde, pero el flujo real `verify() → _breaker.execute(_verifyRaw)` nunca abría el breaker con N fallas consecutivas. La causa: `_verifyRaw` ejecutaba `this._breaker.recordBusinessFailure(code)` (que a su vez hace `this._policy.execute(() => throw)`) **dentro** del wrap externo `this._breaker.execute(() => _verifyRaw(...))`. Cada call producía **+1 failure** (del inner execute) **+1 success** (del outer execute porque `_verifyRaw` retorna un `AdapterResult`, no throw). La SamplingBreaker con threshold 0.5 y `>` estricto nunca supera 50% → jamás trip.
- **Causa raíz**: el pattern "fire-and-forget inner execute" era demasiado clever; rompía el invariante de SamplingBreaker (1 call ↔ 1 outcome). Los tests unit (T-CB-9 con `recordBusinessFailure` puro) no detectaron el bug porque no pasaban por el outer `execute()`.
- **Fix (Opción B del AR)**: introducir `BusinessFailureError extends Error` en `circuit-breaker.ts`. El outer `verify()` / `settle()` ahora envuelve `_verifyRaw` en una lambda que, si el resultado es `SIMULATION_FAILED`/`TRANSACTION_FAILED`, lanza `BusinessFailureError(result, code)` **desde dentro** del `_breaker.execute(lambda)`. Cockatiel cuenta esa throw como 1 failure (clean 1:1). El outer try/catch intercepta `BusinessFailureError`, retorna `err.result` (unwrap), manteniendo la API pública inalterada para los callers. Se eliminó la llamada a `this._breaker.recordBusinessFailure(code)` dentro de `_verifyRaw` (Kite y Avalanche). `recordBusinessFailure` queda como API pública legacy solo para tests que necesiten force-open sin pasar por `execute`.
- **Test de regresión**: `T-ADAPT-CB-6` mockea `_verifyRaw` para retornar siempre `SIMULATION_FAILED`, llama `adapter.verify()` 30 veces via flow real, y assert `adapter._breaker.getState() === 'OPEN'` + la siguiente llamada retorna `CHAIN_UNAVAILABLE 503`. Este test hubiera fallado con la implementación pre-fix.
- **Aplicar en**: cualquier wrap futuro de una `CircuitBreakerPolicy`. REGLA: **nunca** anidar `policy.execute` dentro de otra `policy.execute` del mismo breaker, y **nunca** mezclar "return AdapterResult" con "throw to count as failure" sin traducir explícitamente el AdapterResult a throw en el callsite del outer execute. Si surge una nueva fuente de failures que no sea exception natural (e.g., un status code, un assertion, un polling result), convertirla en throw **antes** del wrap outer, no después.

### [2026-04-23 12:30] Fix-pack post-AR — breakerState emitted when CB_ENABLED=false

- **Error (AR-BLQ-BAJO-1)**: con `CB_ENABLED=false`, `getState()` retornaba `'CLOSED'` (tipado como `BreakerStateName`), por lo que `supported.ts` spread-ponía `breakerState: 'CLOSED'` en la respuesta aunque ese breaker estuviera desactivado. Integradores podían pensar que el chain estaba sano cuando en realidad no había breaker ningúno — violación de DT-7.
- **Causa raíz**: el passthrough mode devolvía un literal placeholder ('CLOSED') en lugar de señalar ausencia; `supported.ts` no distinguía entre "breaker existe y está CLOSED" y "no hay breaker".
- **Fix**: cambiar firma de `ChainCircuitBreaker.getState` a `BreakerStateName | undefined`; retornar `undefined` en passthrough. Propagar la unión en `ChainAdapter.getBreakerState?` (`types.ts`) y en el tipo del getter ducktypeado en `supported.ts`. El spread `...(state !== undefined ? { breakerState: state } : {})` ya estaba bien — omite naturalmente el field cuando undefined.
- **Test de regresión**: `T-RT-SUPPORTED-CB-3` arma un adapter con `getBreakerState: () => undefined` y verifica que `Object.keys(body.chains[0])` NO incluye `'breakerState'`.
- **Aplicar en**: futuras "optional properties derived from adapter state" — preferir `T | undefined` + spread condicional antes que placeholders como `'UNKNOWN'`/`'DISABLED'`. Hace más fácil omitir campos en JSON sin que JSON.stringify los serialice como `null`.

### [2026-04-23 12:30] Fix-pack post-CR — openapi.yaml missing 503 + dead ChainMetadata.breakerState

- **Error (CR-BLQ-BAJO-1 / CR-BLQ-BAJO-2)**:
  1. `doc/openapi.yaml` no documentaba el nuevo response 503 `CHAIN_UNAVAILABLE` en POST /verify ni POST /settle, ni el header `Retry-After`, ni el field optional `breakerState` en `ChainSupportedItem`. Integrators que leían el spec no sabían qué hacer cuando llegara un 503.
  2. `src/chains/types.ts` declaraba `ChainMetadata.breakerState?: ...` pero **ningún** caller lo lee (WFAC-41 pivoteó al ducktype path via `adapter.getBreakerState()`). Type dead-field — el compiler lo acepta, pero induce a lector a creer que existe una ruta estática inexistente.
- **Causa raíz**: 1) los artefactos de documentación no formaron parte del Scope IN original de W1; el archivo `openapi.yaml` quedó rezagado del cambio de código. 2) el field `breakerState` fue agregado temprano (W1) anticipando un approach "stored in metadata", luego se pivoteó (DT-7) al ducktype path, pero el field original nunca fue eliminado.
- **Fix**:
  1. `openapi.yaml`: agregar responses `503` con ejemplo `CHAIN_UNAVAILABLE` + header `Retry-After` en ambas rutas, y property `breakerState` (enum [CLOSED, OPEN, HALF_OPEN], NO en `required`) en `ChainSupportedItem` con description referenciando DT-7.
  2. `types.ts`: eliminar el field muerto `ChainMetadata.breakerState?`. JSDoc reemplazado: "breaker state is NOT stored here; fetched per-request via `adapter.getBreakerState?.()`".
- **Aplicar en**: cualquier HU que agregue un nuevo x402 error code o HTTP status. Checklist: (a) code en `X402ErrorCode` union (`core/types.ts`), (b) `HTTP_BY_CODE` (`core/errors.ts`), (c) responses en `openapi.yaml` para todo path que lo pueda emitir, (d) test en `routes.openapi.test.ts` verificando presencia. También: después de un pivot arquitectónico (como DT-7), cerrar sprint con un grep de `breakerState|<campo-pivoteado>` para detectar restos de la v1 del diseño.
